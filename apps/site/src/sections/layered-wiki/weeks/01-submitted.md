## ① 문제

긴 조직 문서 한 건에는 개인 의견 · 팀 결정 · 일반 지식이 섞여 있다. 이를 개념 단위 노트로 나누고, 노트마다 개인 / 팀 / 전사 중 어느 층에 둘지 정하고, 층 규칙을 지키며 기존 노트와 연결하는 일은 사람이 하면 오래 걸린다. 층을 잘못 두면 하위 층 정보가 위층으로 새어 나간다.

이 문제는 두 목적의 충돌이다.

- 도달성 : 상위 층 노트에서 하위 층 내용에 얼마나 닿을 수 있는가
- 누출 : 하위 층에만 있어야 할 내용이 상위 층 노트에 얼마나 드러나는가

모두 연결하면 도달성이 최대가 되고, 모두 격리하면 누출이 0이 된다. 두 목적이 동시에 걸릴 때만 판단이 필요하고, 그 판단 (어디서 나누고, 어느 층에 두고, 어떤 링크를 만들 것인가) 이 이 프로젝트의 대상이다.

| 적용 대상 | 동아리 · 팀 프로젝트 워크스페이스, 강의 노트 아카이브 |

## ③ 성공 기준

### 지표

| 지표 | 정의 | 단위 |
| --- | --- | --- |
| 배치 정확도 | 세그먼트가 들어간 노트의 층이 사람 정답 층과 같은 비율 | % |
| 도달성 | 상위 층 노트에서 하향 조건부 링크로 닿는 하위 층 세그먼트 비율 | % |
| 누출 | 하위 층 세그먼트에만 있던 고유 표현 (고유명사 · 내부 용어 · 수치) 이 상위 층 노트에 나타난 건수 | 건 |
| 분해 품질 | 같은 노트에 묶인 세그먼트 쌍이 사람이 만든 참조 분해와 일치하는 정도 | % |

네 지표를 볼트 크기 (투입 원본 수 · 볼트 노트 수) 에 대한 곡선으로 낸다. 빈 볼트에서 원본을 한 건씩 무작위 순서로 넣는 순차 성장 평가다.

비교는 조건 4개 (B0 규칙 기반 / B1 단일 프롬프트 / B2 기존 오픈소스 위키 빌더 / 제안) × 모드 2개 (전 층 열람 단일 에이전트 / 층별 인스턴스 분리) 다. 모든 조건은 같은 검색 레이어와 같은 모델을 쓴다. 현재 구현된 조건은 제안 · B1 이고, B0 · B2 는 8주차 시연 뒤에 붙인다. 파일럿 1회 실행 결과 (제안 15문서 × 두 모드, B1 7 / 15 문서) 는 2주 · 6주 개정판에 적었다. 정답 대조 지표 (배치 정확도 · 도달성 · 누출 · 분해 품질) 는 아직 집계하지 않았다.

### 데이터와 정답

- 스냅샷 1차 : 팀 워크스페이스 (개인 페이지 4명 + 회의록 + 산출물), 소프트웨어공학 팀 과제, 강의 노트 4과목. 한 시점에 내보내 SHA-256 으로 고정했다. 팀원 동의를 받았고, 원문은 원격 없는 로컬 저장소에만 둔다.
- 문서 107건을 규칙으로 잘라 세그먼트 1,541개를 만들었다. 파일럿 15건 (세그먼트 176개) / 본실험 92건으로 나눴다.
- 출처 층은 Notion 위치 그대로다 (개인 페이지 → 개인, 팀 공간 → 팀, 강의 노트 → 전사). 정답 층은 라벨링 기준 v2.0 으로 세그먼트마다 사람이 정하고, 정답 = max (출처 층, 고유 층) 으로 합성한다.
- 순서 : 세그먼트 규칙 성문화 → 라벨링 기준 성문화 → 라벨링 → 봉인. 프롬프트 작성 뒤에는 정답셋을 고치지 않는다. 자기 일치도를 재고, 낮으면 정답셋을 버리고 기준부터 다시 쓴다.
- 현재 : 파일럿 라벨링 완료, 본실험 라벨링은 파일럿 뒤.

### 목표 수치를 두지 않는 이유

1. 이 과제는 "몇 % 를 넘긴다" 가 아니라 "조건 사이에 차이가 있는가" 를 묻는다. 차이가 시행 간 흔들림보다 큰지가 먼저다.
2. 그래서 파일럿에서 평균보다 분산을 먼저 잰다. 조건 간 차이가 분산에 묻히면 그 시점에 설계를 고친다.
3. 기준선은 정의로 고정한다. 층별 분리 모드는 설계상 누출 0인 하한선이고, 0이 아니면 그 자체가 버그다.

본실험 문서 수는 원본 1건 처리 시간 (분해 포함) 을 파일럿에서 실측한 뒤 역산한다.

## ④ 왜 에이전트인가

| 신호 | 근거 |
| --- | --- |
| 다단계 | 분해 → 노트마다 볼트 검색 → 배치 판정 → 검수 → 볼트 쓰기 · 로그 |
| 외부 도구 | 볼트 검색 search_vault (읽기), 볼트 쓰기 (검수 통과분만) |
| 외부 지식 | 지금까지 쌓인 볼트 노트가 매 판정의 조회 대상 |
| 반복성 | 원본 문서가 들어올 때마다 같은 절차를 반복 |

단일 호출로 충분하지 않은 이유

1. 한 문서 안에서 노트마다 관련된 기존 노트가 다르다. 문서 전체로 한 번 검색하면 (B1) 노트 하나하나에 맞는 후보를 볼 수 없다. 이 차이는 B1 과 제안을 같은 검색 레이어 · 같은 모델로 비교해 직접 잰다.
2. 같은 문서라도 누가 넣느냐에 따라 보이는 볼트가 다르다. 층별 분리 모드에서는 출처 층 이상, 같은 층은 같은 그룹 (본인 개인 / 소속 팀) 의 노트만 후보로 보인다.
3. 볼트가 시간에 따라 자란다. 앞에 들어간 문서가 만든 노트가 뒤 문서의 후보가 되므로, 같은 문서라도 볼트 크기에 따라 판정이 달라진다. 그래서 결과를 볼트 크기 곡선으로 낸다.

## 범위

- MVP 안 (모두 구현됨) : 층 인식 분해 (출처 세그먼트 기록), 배치 판정, 상향 링크 · 하향 조건부 링크, 모드 2종, 판정 로그, 빌드 필터 (공개 빌드 = 전사 노트만 · 하향 조건부 링크 제거, 로컬 보기 = 보는 사람의 층 × 그룹만). 시연 앞단으로 Dify 워크플로 → 하니스 시연 API 연결
- MVP 밖 : 승격 처리 (설계만 고정), 다중 소스 자동 수집, Notion 실시간 동기화, 스냅샷 2차 평가, 실시간 협업 편집, 인증 · 세션
